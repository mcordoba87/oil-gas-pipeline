PLAN: GENERACIÓN DE DATOS FALSOS MULTI-FUENTE
===============================================================================
Fase 1 - anexo del roadmap_proyecto_petrolera

Motivo: no depender de una sola fuente (MQTT) para que el proyecto simule un
ecosistema realista de datos, típico de una operación petrolera.

Decisiones a definir:
  - Fuente streaming: sensores IoT vía MQTT (SCADA de campo).
  - Fuente batch: CSV diarios (reportes manuales, laboratorio) -> landing en MinIO.
  - Fuente transaccional: Postgres OLTP simulando ERP/CMMS (mantenimiento).
  - Fuente externa: API de precios WTI/Brent + logs de eventos SCADA.
  - Ejecución: cron / programado para las fuentes batch y API.

===============================================================================
INGRESO A - SENSORES IOT (Streaming) -> MQTT
===============================================================================

[x] 1. Simulador de sensores (generators/sensor_simulator.py)
    - Script Python (paho-mqtt) que publica cada X segundos:
        presión, temperatura, caudal (BPD) por pozo.
    - Topics MQTT: pozos/{pozo_id}/presion, pozos/{pozo_id}/temperatura,
      pozos/{pozo_id}/caudal.
    - Incluir ruido/variabilidad realista.
    - Simular problemas de red: paquetes fuera de orden, delays, pérdida de
      mensajes.

[x] 2. Worker de Ingestión (ingestion/mqtt_worker.py)
    - Suscripción a topics MQTT.
    - Parseo y validación de payload (JSON schema).
    - Manejo de datos OUT-OF-ORDER (buffer/watermarking, tolerancia ~5 min).
    - Escritura batch en TimescaleDB (hypertable lecturas_sensores).
    - Copia del dato crudo a MinIO (raw/sensores/) como landing zone.

    RESULTADO: dato IoT entra por MQTT -> se valida y ordena en el worker ->
    cae a TimescaleDB (hot path) y a MinIO como respaldo crudo.

===============================================================================
INGRESO B - CSV DIARIO (Batch) -> LANDING EN MINIO
===============================================================================

[x] 3. Script daily_production_csv.py
    - Genera un CSV diario simulando reportes manuales de producción por pozo:
        pozo_id, fecha, bpd_producido, horas_operativas, observaciones
    - Lo sube a:
        s3://oil-lakehouse/landing/produccion_diaria/YYYY-MM-DD/reporte.csv

[x] 4. Script daily_lab_csv.py
    - Genera un CSV diario simulando análisis de laboratorio (calidad de crudo):
        pozo_id, fecha, grados_api, pct_agua, pct_sedimentos
    - Lo sube a:
        s3://oil-lakehouse/landing/laboratorio/YYYY-MM-DD/analisis.csv
    - Simula el feed manual del ingeniero de yacimiento.
    - SOLO LANDING (sin loader): dbt lo lee directo en Fase 3.
    - Cron DIARIO a una hora fija (ej. 03:00).

===============================================================================
INGRESO C - BASE TRANSACCIONAL (OLTP) -> ERP / CMMS
===============================================================================

[x] 5. Postgres OLTP separado (docker-compose: postgres_oltp)
    - Simula el ERP/CMMS (sistema de mantenimiento) de la empresa.
    - Tablas maestras y transaccionales:
        * pozos (id, nombre, cuenca, fecha_perforacion, estado)
        * mantenimientos (id, pozo_id, fecha, tipo, costo, tecnico)
        * paradas_programadas (id, pozo_id, fecha_inicio, fecha_fin, motivo)

[x] 6. Poblador de datos (generators/seed_oltp.py)
    - Usa Faker (Python) para generar metadata realista de pozos y
      mantenimientos.
    - Actualiza periódicamente estado/mantenimientos para simular operación
      real (útil luego para SCD Type 2 en dbt).

[x] 7. Extractor OLTP -> Lakehouse (ingestion/extract_oltp.py)
    - Job programado (cron) que extrae diariamente pozos/mantenimientos desde
      Postgres OLTP y los deja en s3://oil-lakehouse/raw/oltp/ o los carga
      directo a un esquema raw en TimescaleDB/Postgres analítico.

FASE 3: DATA WAREHOUSE Y TRANSFORMACIONES DBT (ANALYTICS ENGINEERING FOCUS)
------------------------------------------------------------------------------ [x]
[x] 3.1. Inicialización de dbt
    - dbt Core (adapter postgres) contra TimescaleDB en dbt_petrolera/. NOTA:
      dbt-timescaledb requiere Python >=3.11; con Python 3.10 se usa el adapter
      dbt-postgres 1.9 (TimescaleDB es compatible con Postgres).
    - profiles.yml (dbt_petrolera/profiles.yml, credenciales por env vars) y
      dbt_project.yml configurados. Esquemas por capa: staging/intermediate/marts
      (macro generate_schema_name para nombres limpios).
    - Sources definidos: timescale (lecturas, agregados, pozos, cuencas, alertas)
      y raw (tablas cargadas desde MinIO por ingestion/load_landing_to_raw.py:
      producción, laboratorio, OLTP, precios, logs SCADA).
    - dbt-expectations + dbt_utils como paquetes (dbt deps).

[x] 3.2. Capa Staging (Bronze)
    - stg_lecturas_sensores.sql: tipado, dedup por (time, pozo_id), unidades.
    - stg_produccion_diaria.sql: limpieza del CSV de producción (+ gas_mcfd).
    - stg_laboratorio.sql: limpieza del CSV de análisis de laboratorio.
    - stg_pozos.sql / stg_mantenimientos.sql / stg_paradas.sql: normalización
      desde OLTP (mapeo id interno -> pozo_id de negocio).
    - stg_precios.sql: normalización de precios WTI/Brent.
    - stg_scada_logs.sql: normalización de logs semi-estructurados (bonus).

[x] 3.3. Capa Intermediate (Silver)
    - int_lecturas_interpoladas.sql: forward-fill de lecturas perdidas (Postgres
      no soporta IGNORE NULLS; interpolación lineal queda como mejora futura).
    - int_deteccion_outliers.sql: z-score de presión/caudal en ventana móvil 7d.
    - dbt snapshot (snap_pozos_estado): SCD Type 2 sobre estado del pozo.

[x] 3.4. Capa Marts (Gold) - Modelado Dimensional
    - dim_pozos.sql: dimensión de pozos con estado actual e historial + lab.
    - fct_lecturas.sql: hechos de series temporales unificadas (+ cuenca).
    - fct_produccion_diaria.sql: producción acumulada por pozo/cuenca (tabla).
    - fct_boe.sql: BOE = bpd + gas_mcfd/6 (se agregó gas al stack).
    - fct_curvas_declinacion.sql: ajuste exponencial de Arps por pozo vía
      regresión lineal (regr_slope/intercept/r2). Hiperbólica = mejora futura.
    - fct_alertas_anomalias.sql: modelo incremental (alias='alertas') sobre la
      hypertable alertas. Reglas: 1) z-score presión > 3, 2) caída abrupta de
      caudal en ventana 24h, 3) mantenimiento vencido según CMMS por tipo,
      4) lectura fuera de rango físico. Incluye pre-hook de resolución
      (estado abierta -> resuelta cuando la condición desaparece).

[x] 3.5. Testing y Calidad de Datos
    - Tests primarios en models/schema.yml (unique, not_null, accepted_values,
      relationships): 64 tests en total, todos PASAN.
    - dbt_expectations: rangos válidos de presión, temperatura, caudal, gas, BOE.

[x] 4.2. Dashboard exploratorio en Superset
    - Análisis ad-hoc para perfiles de negocio. Apache Superset 5.0.0 (pinned).
    - Conexión a TimescaleDB (todos los esquemas/modelos consultables en SQL Lab:
      staging/intermediate/marts/raw/snapshots/agregados continuos).
    - Provisioning automático (patrón minio-init):
        * superset-init: db upgrade + create-admin + init.
        * superset-provision: REST API registra la database TimescaleDB y crea
          datasets de los 6 marts (dim_pozos, fct_lecturas, fct_produccion_diaria,
          fct_boe, fct_curvas_declinacion, alertas). Idempotente.
    - SQL Lab requiere results backend: se agregó Redis (servicio `redis` + cachelib
      RedisCache en superset/config/superset_config.py).
    - La imagen lean oficial no trae psycopg2: entrypoint.sh lo instala
      (superset/init/requirements-local.txt) en los 3 servicios (corren como root).
    - Acceso: http://localhost:8088 (admin / SUPERSET_ADMIN_PASSWORD).
    - Verificación: bash scripts/verify_superset.sh (health, login, database,
      datasets, query de prueba a marts.fct_boe vía SQL Lab API).

    Consultas ad-hoc de ejemplo (SQL Lab):
      -- BOE por cuenca y día
      SELECT cuenca, fecha, sum(boe_bbl) FROM marts.fct_boe GROUP BY 1,2 ORDER BY 2;
      -- Alertas abiertas por severidad
      SELECT tipo, severidad, count(*) FROM public.alertas
      WHERE estado='abierta' GROUP BY 1,2 ORDER BY 3 DESC;
      -- Curvas de declinación por pozo (mejor ajuste)
      SELECT pozo_id, round(qi_bpd::numeric,1) AS qi, round(tasa_declinacion_d::numeric,4) AS D, r2
      FROM marts.fct_curvas_declinacion ORDER BY r2 DESC;
      -- Producción vs precios WTI
      SELECT d.fecha, sum(d.bpd_producido) AS bpd, avg(p.wti_usd_bbl) AS wti
      FROM marts.fct_produccion_diaria d LEFT JOIN raw.precios p ON p.fecha = d.fecha
      GROUP BY 1 ORDER BY 1;
      -- Mantenimientos correctivos por pozo y estado
      SELECT p.pozo_id, p.cuenca, p.estado_actual, p.n_correctivos
      FROM marts.dim_pozos p ORDER BY p.n_correctivos DESC;
