PLAN: GENERACIÓN DE DATOS FALSOS MULTI-FUENTE
===============================================================================
Fase 1 - anexo del roadmap_proyecto_petrolera

Motivo: no depender de una sola fuente (MQTT) para que el proyecto simule un
ecosistema realista de datos, típico de una operación petrolera.

Decisiones a definir:
  - Fuente streaming: sensores IoT vía MQTT (SCADA de campo).
  - Fuente batch: CSV diarios (reportes manuales, laboratorio) -> landing en MinIO.
  - Fuente transaccional: Postgres OLTP simulando ERP/CMMS (mantenimiento).
  - Fuente externa: API de precios WTI/Brent + logs de eventos SCADA.
  - Ejecución: cron / programado para las fuentes batch y API.

===============================================================================
INGRESO A - SENSORES IOT (Streaming) -> MQTT
===============================================================================

[x] 1. Simulador de sensores (generators/sensor_simulator.py)
    - Script Python (paho-mqtt) que publica cada X segundos:
        presión, temperatura, caudal (BPD) por pozo.
    - Topics MQTT: pozos/{pozo_id}/presion, pozos/{pozo_id}/temperatura,
      pozos/{pozo_id}/caudal.
    - Incluir ruido/variabilidad realista.
    - Simular problemas de red: paquetes fuera de orden, delays, pérdida de
      mensajes.

[x] 2. Worker de Ingestión (ingestion/mqtt_worker.py)
    - Suscripción a topics MQTT.
    - Parseo y validación de payload (JSON schema).
    - Manejo de datos OUT-OF-ORDER (buffer/watermarking, tolerancia ~5 min).
    - Escritura batch en TimescaleDB (hypertable lecturas_sensores).
    - Copia del dato crudo a MinIO (raw/sensores/) como landing zone.

    RESULTADO: dato IoT entra por MQTT -> se valida y ordena en el worker ->
    cae a TimescaleDB (hot path) y a MinIO como respaldo crudo.

===============================================================================
INGRESO B - CSV DIARIO (Batch) -> LANDING EN MINIO
===============================================================================

[x] 3. Script daily_production_csv.py
    - Genera un CSV diario simulando reportes manuales de producción por pozo:
        pozo_id, fecha, bpd_producido, horas_operativas, observaciones
    - Lo sube a:
        s3://oil-lakehouse/landing/produccion_diaria/YYYY-MM-DD/reporte.csv

[x] 4. Script daily_lab_csv.py
    - Genera un CSV diario simulando análisis de laboratorio (calidad de crudo):
        pozo_id, fecha, grados_api, pct_agua, pct_sedimentos
    - Lo sube a:
        s3://oil-lakehouse/landing/laboratorio/YYYY-MM-DD/analisis.csv
    - Simula el feed manual del ingeniero de yacimiento.
    - SOLO LANDING (sin loader): dbt lo lee directo en Fase 3.
    - Cron DIARIO a una hora fija (ej. 03:00).

===============================================================================
INGRESO C - BASE TRANSACCIONAL (OLTP) -> ERP / CMMS
===============================================================================

[x] 5. Postgres OLTP separado (docker-compose: postgres_oltp)
    - Simula el ERP/CMMS (sistema de mantenimiento) de la empresa.
    - Tablas maestras y transaccionales:
        * pozos (id, nombre, cuenca, fecha_perforacion, estado)
        * mantenimientos (id, pozo_id, fecha, tipo, costo, tecnico)
        * paradas_programadas (id, pozo_id, fecha_inicio, fecha_fin, motivo)

[x] 6. Poblador de datos (generators/seed_oltp.py)
    - Usa Faker (Python) para generar metadata realista de pozos y
      mantenimientos.
    - Actualiza periódicamente estado/mantenimientos para simular operación
      real (útil luego para SCD Type 2 en dbt).

[x] 7. Extractor OLTP -> Lakehouse (ingestion/extract_oltp.py)
    - Job programado (cron) que extrae diariamente pozos/mantenimientos desde
      Postgres OLTP y los deja en s3://oil-lakehouse/raw/oltp/ o los carga
      directo a un esquema raw en TimescaleDB/Postgres analítico.

FASE 3: DATA WAREHOUSE Y TRANSFORMACIONES DBT (ANALYTICS ENGINEERING FOCUS)
-------------------------------------------------------------------------------
[ ] 3.1. Inicialización de dbt
    - dbt-timescale contra TimescaleDB en dbt_petrolera/.
    - profiles.yml y dbt_project.yml configurados.
    - Definir sources: mqtt/timescale (lecturas), landing CSV (producción,
      laboratorio), raw OLTP (pozos, mantenimientos), raw precios/logs.

[ ] 3.2. Capa Staging (Bronze)
    - stg_lecturas_sensores.sql: tipado, normalización de unidades (psi,
      °F/°C, BPD), dedup por timestamp+pozo.
    - stg_produccion_diaria.sql: limpieza del CSV de producción.
    - stg_laboratorio.sql: limpieza del CSV de análisis de laboratorio.
    - stg_pozos.sql / stg_mantenimientos.sql: normalización desde OLTP.
    - stg_precios.sql: normalización de precios WTI/Brent.

[ ] 3.3. Capa Intermediate (Silver)
    - int_lecturas_interpoladas.sql: interpolación de lecturas perdidas
      (forward-fill / interpolación lineal).
    - int_deteccion_outliers.sql: flagging de outliers en presión/caudal.
    - dbt snapshot (snap_pozos_estado): SCD Type 2 sobre estado del pozo.

[ ] 3.4. Capa Marts (Gold) - Modelado Dimensional
    - dim_pozos.sql: dimensión de pozos con estado actual e historial.
    - fct_lecturas.sql: hechos de series temporales unificadas.
    - fct_produccion_diaria.sql: producción acumulada por pozo/cuenca.
    - fct_boe.sql: cálculo de Barriles Equivalentes de Petróleo (BOE),
      conversión gas/petróleo a unidad común.
    - fct_curvas_declinacion.sql: ajuste de curvas de declinación (Arps:
      exponencial/hiperbólica) por pozo y cuenca.
    - fct_alertas_anomalias.sql: alertas por reglas:
        1) desviación estándar de presión > umbral (z-score > 3)
        2) caída abrupta de caudal en ventana móvil
        3) mantenimiento vencido según CMMS
        4) lectura fuera de rango físico esperado

[ ] 3.5. Testing y Calidad de Datos
    - Tests primarios en schema.yml (unique, not_null).
    - dbt_expectations: rangos válidos de presión, temperatura, BOE >= 0.
